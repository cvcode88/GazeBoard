Gaze Board

A cheap, Raspberry-Pi-deployable eye-gaze AAC (augmentative & alternative communication) keyboard — built as a browser prototype first, with a parallel Python/Pygame version aimed at the actual target hardware.

Why it exists

Dedicated eye-gaze communication devices are expensive — often thousands of dollars — which puts them out of reach for a lot of people who could benefit from one. Gaze Board's premise: a Raspberry Pi and a normal webcam or Pi camera, running free, open software, can get meaningfully close for a fraction of the cost.

Two implementations, one goal

Browser prototype (this file's subject) A single self-contained HTML/JS/CSS page. Started as a mouse-driven mockup of the interaction model, later grew a genuine real-time webcam eye tracker (WebGazer.js) bolted on. Fast to iterate on, easy to demo from any laptop.
Python / Pygame (the real target) gaze_board.py, predictor.py, profiles.py — the version meant to actually run on a Raspberry Pi. No browser sandbox restrictions to fight, direct camera access, the intended long-term home for real eye tracking.

Core interaction model

Both versions share the same idea: a key (or button) highlights under wherever the person is looking, and gets selected one of two ways:

  • Typing mode (dwell): hold your gaze on a key for a set amount of time (the dwell time) and it commits automatically. An adaptive-timing system nudges that duration up or down over time based on how often the person overshoots or hesitates.
  • Blink mode (switch): gaze only highlights; a separate discrete action — a click standing in for a real blink or external switch — confirms the selection. This avoids the classic "Midas touch" problem (accidentally selecting everything you glance at).

Every other system in the project — predictive text, calibration, the real webcam tracker — plugs into this same highlight/commit pipeline rather than reinventing it.

Interaction

Keyboard & selection

A layout designed around how often letters are actually used, and a selection model built to tolerate an imprecise pointer.

Frequency-optimized layout

Letters aren't arranged QWERTY-style. Each key's position is chosen from real English letter-frequency data (E, T, A, O, I... down to Q, Z), and cells are ranked by distance from the grid's center. The most frequent letters land in the most central, easiest-to-reach cells — the ones a wandering, imprecise gaze estimate is most likely to land on correctly — and key size scales with that same frequency, so common letters are also physically bigger targets.

var LETTER_FREQ = [
  ['E',12.70],['T',9.06],['A',8.17],['O',7.51],['I',6.97],['N',6.75],
  ['S',6.33],['H',6.09],['R',5.99], // ...down to Q, Z
];

Dwell timing + the adaptive AI

Dwell time isn't one fixed number for everyone. A short calibration flow measures how long it takes a specific person to reliably fixate on a target, and that becomes their starting dwell time. From there, an adaptive system watches ongoing behavior — backspace rate, hesitation, overshoot — and nudges the dwell time up (more forgiving) or down (faster typing) automatically over a session.

Blink mode

Suggestions, the favorite-star button, and the favorites list are always blink-only, regardless of the global typing/blink setting — gaze can rest on them to read without ever accidentally selecting one. Everywhere else, "blink" is simulated with a click, which is also exactly the signal a real external switch would send.

Intelligence

Predictive text

Three layered systems, from cheapest to smartest, so there's always a reasonable guess even when the smarter ones have nothing to say.

flowchart TD
    A["Person is typing a word,\nor about to start one"] --> B{"Nearest CONTENT word\nbefore the blank\n(skipping stopwords)\nmatches CONTEXT_ASSOCIATIONS?"}
    B -- yes --> C["Use that word list first\n('pet' -> dog, cat, puppy...')"]
    B -- no / not enough --> D{"Immediately previous word\nis in COMMON_BIGRAMS?"}
    D -- yes --> E["Use that word list\n('the' -> door, water, tv...')"]
    D -- no / not enough --> F["Fall back to raw dictionary\nfrequency, prefix-matched"]
    C --> G["Merge, dedupe, cap at 6\nsuggestions - #1 becomes\nthe ghost-text guess"]
    E --> G
    F --> G

1. Next-letter highlighting

While a word is being typed, the keyboard highlights which next letters are plausible — not full words, just individual keys — using approxZipf(), a frequency estimate reconstructed straight from a word's rank in a pre-sorted ~235k-word dictionary (most-common-word-first). No server, no live computation over the whole dictionary at runtime beyond a scan for matching prefixes.

function approxZipf(rank){
  return Math.max(0.8, 7.6 - Math.log2(rank + 2) * 0.85);
}

2. Bigram-based word suggestions

A hand-picked table of ~60 common words, each mapped to the words most likely to follow it (COMMON_BIGRAMS), several deliberately skewed toward AAC phrasing — need → help, feel → sick/tired/better. This is the same core idea predictive keyboards used before neural language models: rank candidates by how often word B follows word A.

3. Context associations — the "pet the dog" fix

A plain bigram only ever looks at the single immediately-preceding word — and that word is very often a stopword that can't disambiguate anything. i pet the d— and i open the d— both have "the" as their previous word, so a pure bigram model treats them identically and just returns whatever COMMON_BIGRAMS['the'] happens to list first.

The bug, concretelyCOMMON_BIGRAMS['the'] lists door but not dog — so the ghost text confidently suggested "door" after "i pet the d", regardless of context, because "the" alone genuinely can't tell those two sentences apart.

nearestContextWord() fixes this by scanning backward past stopwords (the, a, my, to, is...) to find the nearest real content word — "pet", two words back — and checking a separate association table keyed on that:

var CONTEXT_ASSOCIATIONS = {
  pet:   ['dog','cat','puppy','kitten','rabbit'],
  drink: ['water','juice','milk','soda','coffee'],
  feel:  ['sick','tired','happy','sad','hungry','thirsty'],
  need:  ['help','water','bathroom','break','medicine','rest'],
  // ...
};

function nearestContextWord(){
  var before = buffer.slice(0, buffer.length - currentWord().length);
  var words = before.trim().split(/[^a-zA-Z]+/).filter(Boolean);
  for (var i = words.length - 1; i >= 0; i--) {
    var w = words[i].toLowerCase();
    if (!CONTEXT_STOPWORDS[w]) return w; // skip "the", "a", "to"...
  }
  return '';
}

Checked before the bigram table and the dictionary fallback, for both the suggestion chips and the single best ghost-text guess — so "i pet the d" now genuinely completes to "dog".

Ghost text

The greyed-out preview after the cursor. Mid-word, it's the tail end of the best matching suggestion; at the start of a new word, it's a whole predicted word from the context/bigram tables. Accepting it replaces the whole current word (case-normalized) rather than naively appending, which avoids garbage like HELlo when keys commit uppercase but the dictionary is lowercase.

Calibration

Two entirely different calibrations live in this app, measuring two entirely different things.

CalibrationWhat it measuresFeeds into
Dwell timingHow long it takes this person to reliably fixate on a targetStarting dwell time + the adaptive-timing AI
Gaze position (WebGazer)How this face/webcam/lighting/seating maps to actual screen coordinatesWebGazer's own ridge-regression model

Gaze-position calibration flow

Fully hands-free by design — no clicking anywhere, since asking a gaze-only user to also click defeats the point. Three phases, run back to back:

  1. Grid sweep — a user-chosen grid (3×3 quick, 5×5 standard, 7×7 thorough) of fixed points, each one held-gaze-and-capture, run for several full round-robin rounds.
  2. Edge sweep — the dot glides smoothly in a snake pattern from the literal top-left corner (rendered genuinely half-clipped off the viewport, since CSS centers it exactly on the edge) across and down the whole screen, covering true extremes the grid's comfortable margins never reach.
  3. Free-roam — the dot drifts to random points with eased interpolation for ~20 seconds, for a final burst of varied, less-predictable training data.
A real bug found the hard way Early versions calibrated point-by-point, spending many samples on point 1, then point 2, and so on. WebGazer's ridge regression keeps only its last 50 training samples — a fixed-size ring buffer, confirmed straight from its source (InitRegression hardcodes var e = 50). Sweeping top-to-bottom meant the buffer, by the end, held almost nothing but the last few (bottom-row) points — so predictions stuck near the bottom of the screen no matter where the person actually looked.
The fix Round-robin sampling: sweep every point in the set taking only 1–2 samples each, then loop back and sweep again for more rounds. The buffer's last ~50 samples are then always a fresh, even spread across the whole grid — never just wherever the sweep happened to end.

Smooth pursuit — a real technique, not an improvisation

Having a target move continuously while assuming the eyes are tracking it is an established eye-tracking calibration method, not something invented for this project. WebGazer needs the same ground truth either way — a screen position, paired with an eye reading at that instant — a moving point supplies that exactly as well as a held-still one, provided the motion stays slow enough to actually follow.

Eye tracking

Real webcam tracking

Genuine, real-time gaze estimation from an ordinary webcam, via WebGazer.js (Brown University, open source since 2016) — and the platform walls that had to be worked around to get it running at all.

How it's wired in

The library loads from jsdelivr as an ordinary <script> tag, resolves a webgazer global, and its gaze-listener callback feeds coordinates into the exact same blob-driven hit-testing system the simulated dev-mode blob already used — so real tracking, once running, drives the whole app (keys, dock buttons, suggestions, favorites) through code that was never rewritten for it.

Wall #1 — cross-origin runtime fetches

WebGazer's face-tracking backend (MediaPipe FaceMesh) needs to download WASM binaries and model data after the main script loads. Claude's Artifact sandbox blocks that kind of secondary cross-origin fetch outright — silently, with no visible error — even from the same CDN the script itself came from.

The fix WebGazer's default asset path (faceMeshSolutionPath: "./mediapipe/face_mesh") is relative to the page, not hardcoded to an external host — confirmed by reading WebGazer's actual source. Downloading those ~16 MB of model/WASM files once and republishing them as the artifact's own files, at that exact relative path, means the same-origin fetch succeeds where the cross-origin one was blocked. No patching of WebGazer itself required.

Wall #2 — camera permission policy

Separately, and unrelated to the fetch issue: Claude's hosting appears to send a Permissions-Policy that blocks camera access for artifact pages outright. The telltale sign was a NotAllowedError with no permission popup ever appearing — not even after manually setting the browser's site permission to Allow, which rules out a simple remembered "block" decision and points to the page itself never being allowed to ask.

Eye tracking

Dev tools & simulation

A restricted tab (any signed-in profile, originally two named testers) for testing gaze-driven interaction without needing a working webcam tracker at all.

Simulated webcam blob

Replaces the small precise gaze dot with a wandering, imprecise blob that approximates what a real low-cost camera actually outputs — grounded in published research, not guessed:

  • Error floor: ~100–340px, pulled from real WebGazer.js/study accuracy figures (sparse-calibration vs. well-lit calibrated conditions). A dedicated IR tracker like the Gazepoint GP3 HD manages ~35–40px — meaningfully tighter, because it's fundamentally different hardware.
  • Confidence coloring: a genuine two-tone radial gradient — blue at low confidence, orange at high — center pulling toward the "confident" color and edge toward "uncertain", both colorblind-safe since the signal is opacity/position, not hue alone.
  • Shape: a little taller than wide even at rest (video-based trackers measure vertical gaze less precisely — smaller range of motion, harder to detect), stretching further along the current heading the faster it moves (frame-rate + processing lag blur fast eye movement).

The webcam quality slider

Scales that error floor between a "rough, uncalibrated webcam" and "best-case, calibrated webcam" — both ends are the actual published figures above, not arbitrary slider math.

The easter egg

Undocumented anywhere in the UI: favoriting the exact phrase AYDDYKHMMTI toggles a screen-shake + slow rainbow glow effect; unfavoriting turns it off. Deliberately not a strobe or flash effect — rapid high-contrast flashing is a documented photosensitive-epilepsy trigger, and this is an accessibility tool. The rainbow glow's full hue cycle takes ~6 seconds, nowhere near the ~3-times-a-second range that's an actual seizure risk.

Platform

Accounts & sync

Three layered ways to sign in, from "just this browser" up to "any device, same Claude org."

flowchart LR
    A["Sign-in screen"] --> B["Continue with\nClaude account"]
    A --> C["Username + password"]
    B --> D["Private per-viewer doc\ndata/users/<id>/profile\n(Claude db capability)"]
    C --> E{"Shared cloud doc found?\naccounts/<sha256 username>"}
    E -- yes --> F["Load from cloud,\nmirror future saves back"]
    E -- no --> G["Fall back to this\nbrowser's localStorage"]

Local accounts (always available)

Username + password, hashed (SHA-256) before ever touching storage, saved to localStorage. Zero server, zero dependency on the hosting platform — works identically on the Claude artifact, GitHub Pages, or a local file. The tradeoff: strictly per-browser.

Claude-account sign-in

Uses the Artifact platform's user + db capabilities: user.id() gives an opaque per-organization id, and profile data lives at the private path data/users/<id>/profile — invisible to every other viewer, including the artifact's own owner. No password needed; the Claude sign-in itself is the credential. Only works inside claude.ai, and only reaches other devices signed into the same Claude account.

Cross-device username/password sync

The same local username/password flow additionally mirrors to a shared (not private) document at accounts/<sha256 of the username>, so the exact same credentials work from a different device — as long as that device is also signed into a Claude account in the same organization as the artifact's owner. Genuinely different, unrelated Claude accounts/organizations cannot reach each other's data this way; that's a hard platform boundary, not a bug.

A real bug found the hard way The platform's db capability hands back frozen document objects from .data() — the platform's own contract says to clone before editing. The very first sign-in after loading cloud data would throw TypeError: "x" is read-only the moment anything tried to write a favorite, a setting, or a stat, since that data was being mutated in place. Fixed by deep-cloning (JSON.parse(JSON.stringify(...))) immediately after every cloud read, before it's ever assigned to live state.
Platform

Appearance & accessibility

Every visual choice here is either a genuine accessibility feature or grounded in real research — nothing is purely decorative.

Accent colors & dark mode

Eight accent presets, each with its own light and dark variant, applied as inline CSS custom properties (--accent, --accent-strong, --accent-rgb) on the root element — inline styles always win over stylesheet rules, which is what lets one chosen color follow the person across both themes without fighting the cascade.

High contrast

Bumps border and muted-text visibility using the same inline-custom-property technique, independent of light/dark mode.

Colorblind-safe confidence color

The default amber confidence color is colorblind-safe on its own merits: confidence is communicated through opacity on a single hue, not by picking between two different hues the way a red/green pair would be — the single most common form of color blindness would still read it fine. A blue alternative is offered regardless, for anyone who finds it easier to parse.

Platform

Stats & charts

Session and all-time metrics, plus hand-rolled trend charts — no charting library, just inline SVG.

What's tracked

Session: time, characters typed, words completed, current WPM, backspace rate, dwell time. All-time: blends persisted totals with the still-in-progress current session, so the numbers never look like they're ignoring what was just typed.

Trend charts

Three sparklines built from the same adaptiveHistory array every session already recorded to (WPM, dwell time, backspace rate) — a small hand-written SVG path generator (buildSparklineSVG) maps each value to its own min/max range and draws a filled line chart, no dependency needed for three thin trend lines.

Shipping it

Deployment

Three ways to run this, in order of how much platform restriction stands between you and a working camera.

Claude artifact link

Zero setup, works instantly, best for the localStorage/keyboard/prediction experience — but real webcam tracking is blocked by Claude's own hosting policy (see Real Webcam Tracking).

GitHub Pages

  1. New public repo → uploading an existing file → drag in gaze-board.html, dictionary.js, and the whole mediapipe folder (keeping it a folder, not flattened) → commit.
  2. Repo Settings → Pages → Source: Deploy from a branch → Branch: main, / (root) → Save.
  3. Wait ~1 minute, visit the printed github.io URL + /gaze-board.html (add the extra folder segment if the files ended up nested one level deep).

Every future change needs a fresh upload of the changed file(s) — GitHub Pages does not auto-sync with anything.

Local server

python -m http.server 8000
# then open http://localhost:8000/gaze-board.html

Fastest way to test changes instantly, with full camera access and no upload step — the tradeoff is it only works on the machine actually running the server.

Raspberry Pi (the real target)

Two paths: run the Python/Pygame version directly against a Pi camera (no browser sandbox to fight at all), or run this HTML version in the Pi's own local Chromium in kiosk mode — the same "local server, no platform restrictions" reasoning applies on-device as it does on a laptop.
